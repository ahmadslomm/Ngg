## 3. Schema / migration

```prisma
model RoomTheme {
  id        Int     @id             // explicit ids (match captured theme ids); config-as-data
  name      String  @db.VarChar(64)
  skinUrl   String?                 // room background / skin asset
  bubbleUrl String?                 // themed chat-bubble asset (optional)
  sort      Int     @default(0)
  enabled   Boolean @default(true)
  rooms     Room[]
  @@index([enabled, sort])
}
// Room:
themeId Int?
theme   RoomTheme? @relation(fields: [themeId], references: [id], onDelete: SetNull) // T2.6
```

Migration `20260712141451_room_theme`:
- `CREATE TABLE "RoomTheme"` + `RoomTheme_enabled_sort_idx`.
- `ALTER TABLE "Room" ADD CONSTRAINT "Room_themeId_fkey" FOREIGN KEY ("themeId") REFERENCES "RoomTheme"("id") ON DELETE SET NULL ON UPDATE CASCADE`.

**This is the FK the task requires** ("validate `Room.themeId` FK") — a deliberate departure from the T1.16 scalar-no-FK pattern, applied to `Room.themeId` **only**. It applied **cleanly**: every existing `Room.themeId` is `null` (the column shipped in T1.16 as an unused scalar), so no row violates the new constraint, and no data backfill/reset was needed. `ON DELETE SET NULL` means retiring a theme safely nulls referencing rooms (they fall back to the default skin) rather than blocking the delete. **No other FK was added.**

## 4. Implementation

**Repo boundary (`room.repo.ts` + `room.prisma-repo.ts`):**
- `RoomRecord` gains `themeId: number | null`; a new `RoomTheme` type `{ id, name, skinUrl, bubbleUrl }` is the client-facing skin descriptor.
- `getTheme(themeId)` returns an **enabled** theme or `null` (missing/disabled); `setRoomTheme(roomId, themeId)` writes `Room.themeId`.
- Prisma impl: `getTheme` = `roomTheme.findFirst({ where: { id, enabled: true } })`; `setRoomTheme` = `room.update({ data: { themeId } })`; both `RoomRecord` builders now carry `themeId`.
- In-memory impl: a `themes` map + an `addTheme(...)` test helper (mirrors seeding a row); `getTheme` honors `enabled`.

**Service (`room.service.ts`):**
- `roomMeta` now includes `theme_id: room.themeId`, so **every** payload that already carries room metadata (`join`, `getSeats`) reflects the theme — additive, backward-compatible.
- `setTheme(roomId, actorId, themeId)`:
  1. room exists (else `room_unavailable`);
  2. **`EDIT_ROOM` permission** via the existing `requirePermission` (owner bypasses; a non-zero member bitmap must include the bit; else role fallback);
  3. a non-null `themeId` must resolve via `repo.getTheme` (else `invalid_theme`); `null` clears;
  4. persist via `repo.setRoomTheme`, then emit **`room.updated`** with `{ room_id, theme_id, theme }`;
  5. return `{ theme_id, theme }` for the HTTP reply.

**Route (`room.routes.ts`):** `POST /rooms/:id/theme`, body `{ theme_id: int>0 | null }`, authenticated; `invalid_theme` mapped to **400**. Follows the existing `fail(reply, error)` convention exactly.

**Events (`room.events.ts`):** added `RoomUpdated: 'room.updated'` + `roomUpdated()` builder. All prior event names (`seat.update`/`mic.update`/`role.changed`/`user.kicked`/`room.joined`/`room.left`/`seat.invited`) are preserved **verbatim** — this is purely additive.

## 6. Tests added (`room-theme.api.test.ts`, 7 — api, in-memory repo like room.api.test.ts)

1. **owner sets a valid theme** → 200 with `{theme_id, theme}`; a **`room.updated`** event on `room:<id>` carrying the theme; a subsequent `getSeats` reflects `theme_id`.
2. **fresh room** → `theme_id: null` in its payload.
3. **unknown theme_id** → 400 `invalid_theme`; **no** `room.updated`; payload unchanged.
4. **disabled theme** → 400 `invalid_theme` (treated like unknown).
5. **clear (theme_id:null)** → 200, `theme: null`, `room.updated` with null theme, payload reset.
6. **non-owner without EDIT_ROOM** → 403; no event; theme unchanged.
7. **missing room** → 404 `room_unavailable`.

*No isolation base needed:* the api test uses the in-memory repo (no shared DB), like `room.api.test.ts`.
