## 3. Schema / migration

```prisma
model LevelConfig {
  id      Int     @id @default(autoincrement())
  kind    Int     // 0 charm, 1 wealth
  level   Int     // tier number (1..N), ascending with minExp
  minExp  BigInt  // inclusive lower bound: exp >= minExp qualifies for this tier
  name    String  @db.VarChar(64) // display name (source of Profile.charmLevelName / wealthLevelName)
  iconUrl String?
  @@unique([kind, level])
  @@index([kind, minExp])
}
```

Standalone model — **no** `Profile` relation/FK, no change to `Profile` at all. Migration `20260712140023_level_config` is **purely additive**: one `CREATE TABLE` + `LevelConfig_kind_minExp_idx` (resolver lookup path) + `LevelConfig_kind_level_key` (unique guard). **No `ALTER TABLE Profile`.** Applied clean (migrate status clean at 14 beforehand → no reset); DB in sync at **15**.

## 4. Resolver design (`level.service.ts`)

```ts
resolveLevel(kind, exp) → { level, name, iconUrl }
```

- **Lookup, not math:** `findFirst({ where: { kind, minExp: { lte: exp } }, orderBy: [{ minExp: 'desc' }, { level: 'desc' }] })` — the **highest configured tier** whose `minExp <= exp`. `LevelConfig` is the only source consulted (no in-memory ladder, no hard-coded fallback thresholds — your confirmation).
- **Inclusive boundary:** `exp == minExp` qualifies for that tier; `minExp` ties break by higher `level` (deterministic).
- **Safe fallback:** an empty ladder (no rows for `kind`), or an `exp` below the lowest tier, → `{ level: 0, name: null, iconUrl: null }`. Never throws. A negative `exp` is clamped to `0` first.
- **Both ladders, one table:** `kind` (0 charm, 1 wealth) discriminates; `resolveCharmLevel(exp)`/`resolveWealthLevel(exp)` are thin wrappers over kinds 0/1, exported alongside `LEVEL_KIND`.
- **Read-only:** the resolver does not write `Profile` or recompute stored levels — wiring it into the profile read/update path (or a level-recompute on exp change) touches `users.service.ts`/`gift.service.ts`, **outside the T2.5 file list**, and is intentionally **deferred** (same deferral discipline as T2.4's accumulate wiring). The T2.5 test surface, per the task spec, is the resolver service itself.

## 6. Tests added (`level.service.test.ts`, 6)

1. **exp → tier + name** — mid-range picks the correct tier; above the top stays at the top tier; `exp 0` on a `minExp 0` tier → level 1 with its name/icon.
2. **inclusive boundary** — `exp == minExp` → that tier; one below → the previous tier (checked at two boundaries).
3. **below the lowest tier → level 0** — a ladder that starts at `minExp 1000` returns `{level:0,name:null}` for exp `0`/`999`; a negative exp clamps to 0 → fallback.
4. **empty ladder → level 0** — a `kind` with no rows resolves to fallback even for a huge exp.
5. **kind isolation** — two independent ladders (distinct kinds) resolve to their own names; neither leaks the other's tiers.
6. **wrappers** — `LEVEL_KIND.CHARM/WEALTH` are 0/1; `resolveCharmLevel`/`resolveWealthLevel` return a valid `ResolvedLevel` (numeric `level >= 0`) and never throw.

*Isolation:* `LevelConfig` rows persist across runs and share the real charm/wealth kinds (0/1), so each test uses a **random per-run `kind` base** (`KIND_BASE = 100_000 + random`), making its ladder invisible to the seed + other runs — the fixed-id isolation pattern from T2.1/T2.4. **Verified stable across two consecutive isolated runs (6/6 each).**
