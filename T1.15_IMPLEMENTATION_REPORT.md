## 3. Gift send flow (complete)

```
POST /gifts/send  { gift_id, qty, room_id?, recipient_ids[], use_bag? }   (auth required)
  → sendGift({ senderId, roomId, giftId, qty, recipientIds, idempotencyKey, useBag })
    serializableTx:
      0. idempotency: if idempotencyKey already in walletLedger → throw idempotent_replay (→ API 200 replay)
      1. gift = Gift.findUnique; must exist & enabled              (server-authoritative price)
      2. unitPrice = gift.priceCoins ; totalCoins = unitPrice × qty × |recipients|

      ── if use_bag ─────────────────────────────  (NEW — bag funding)
         need = qty × |recipients|
         bag = UserGiftBag[sender,gift]; require LIVE (qty ≥ need AND not expired) else insufficient_bag
         bag.qty -= need                                          (decrement, no coins)
         WalletLedger += { coins, delta 0, balanceAfter=coinsNow, reason gift_send, refType 'gift_bag', idemKey }
         each recipient: Profile.charmExp += unitPrice×qty         (CHARM ONLY — no beans)
         GiftTransaction += (notional totalCoins)
         → return { senderCoinsAfter = coinsNow (unchanged), event: gift.received, lucky: undefined }

      ── else (coins funding, pre-existing) ─────────
         require wallet.coins ≥ totalCoins else insufficient_coins
         wallet.coins -= totalCoins (version++) ; WalletLedger += { coins, delta −total, reason gift_send }
         Profile.wealthExp += totalCoins
         each recipient: wallet.beans += unitPrice×qty ; WalletLedger += { beans, +… , reason gift_recv } ; Profile.charmExp += …
         lucky (category 2): roll multiplier → credit coins back + LUCKY_WIN ledger row
         GiftTransaction += ; → return { …, event: gift.received, lucky? }

  → route: if event.room → emitRoomEvent(gift.received)           (broadcast core, both paths)
  → route: leaderboards / combo / rocket / bomb  (pre-existing EFFECTS — unchanged, out of T1.15 scope)
```

## 4. Transaction boundaries

Both funding paths run inside the **same `serializableTx`** used before — one SERIALIZABLE Postgres transaction. Every write (bag decrement, ledger row, charm increment, `GiftTransaction`) commits or rolls back together. **Atomicity proven by test:** `insufficient_coins` and `insufficient_bag` both leave zero partial writes (balance/qty unchanged, no `GiftTransaction`). The DB `CHECK(coins ≥ 0)` remains the backstop on the coins path; the bag path guards `qty ≥ need` before decrementing.
