## 3. Schema / migration

```prisma
model RoomPk {
  id        BigInt    @id @default(autoincrement())
  roomId    BigInt    // scalar ref, no FK
  status    Int       @default(0) // 0 active, 1 settled
  aUserId   BigInt    // side A competitor (scalar ref, no FK)
  bUserId   BigInt    // side B competitor (scalar ref, no FK)
  aScore    BigInt    @default(0)
  bScore    BigInt    @default(0)
  winnerId  BigInt?   // set on settle; null = draw (or not yet settled)
  version   Int       @default(0) // optimistic guard — settle computes the outcome exactly once
  startedAt DateTime  @default(now())
  endsAt    DateTime
  settledAt DateTime?
  @@index([roomId, status])
  @@index([status, endsAt])
}
```

## 4. Battle design & flow

A battle is a two-sided contest **inside one room**: `aUserId` vs `bUserId`. Gifts landing on a competitor during the battle grow that side's score; at `endsAt` the higher score wins (equal = draw).

**`startPk({ roomId, aUserId, bUserId, durationSec })`:**
- Guards: `durationSec > 0` (else `invalid_duration`); `a != b` (else `invalid_sides`); the room exists (else `room_unavailable`); **no other active battle** in the room (else `pk_active`).
- Creates the snapshot (`status 0`, `endsAt = now + durationSec`).
- **Enqueues the delayed settle**: `enqueue(QUEUE.rooms, 'pk-settle', { pkId }, { delay: durationMs, jobId: 'rooms:pk-settle:<pkId>' })` — fires at `endsAt`. `jobId` dedupes to one settle per battle; best-effort (a queue hiccup never fails the start — the version guard + a later settle still close it correctly).
- Emits `pk.updated` (phase `started`).

**`accumulate(roomId, recipientId, coins)` — the gift-send hook:**
- Ignores non-positive `coins`. Finds the room's active battle; **inert** if none.
- If `recipientId` is `aUserId` → side `a`; `bUserId` → side `b`; otherwise **inert** (a gift to a non-competitor doesn't score).
- **Atomic, status-guarded increment** — `updateMany({ where:{ id, status:0 }, data:{ aScore|bScore: { increment: coins } } })`. Race-safe: Postgres serializes the row update, so **N concurrent gifts sum exactly** (proven: 25 parallel → 2500). A battle that settled between the read and the write matches 0 rows → no late score.
- Best-effort `pk.updated` (phase `score`) with live scores.

**`settle(pkId)` — outcome exactly once:**
- No-op if the battle is missing or already `status 1`.
- Computes `draw = aScore == bScore`; `winnerId = draw ? null : (aScore > bScore ? aUserId : bUserId)`.
- Inside `serializableTx`, a **version-guarded** `updateMany({ where:{ id, status:0, version }, data:{ status:1, winnerId, settledAt, version:increment } })`. `count === 1` → **we settled**; a concurrent/duplicate settle (delayed job vs manual) matches 0 rows and no-ops. ⇒ **the outcome is computed exactly once** (proven: 8 parallel settles → exactly 1 `settled:true`).
- **No money/ledger** — records the outcome only (per the task's "computes outcome" and your confirmation). Emits `pk.updated` (phase `settled`, with `winner_id`/`draw`).

## 5. Worker — `pk-settle.ts`

Consumes the **delayed** `rooms:pk-settle` job (QUEUE.rooms) that `startPk` enqueues per battle:
- `pkSettleProcessor` — reads `job.data.pkId`, ignores other rooms-queue job names, and calls `settle(pkId)`.
- `runPkSettle(pkId)` — thin wrapper over `settle` (observability/tests).
- `registerPkSettleWorker()` — the T1.3 `registerWorker` hook. **Not wired into `workers/index.ts` main** (the same deferral as T2.2/T2.4). Unlike the vip/pool sweeps this is **not** a repeatable schedule — each battle enqueues its own one-shot delayed job at start.

## 6. WS events

| Event | Phase | Emitted by | Payload |
|---|---|---|---|
| `pk.updated` | `started` | `startPk` | snapshot (ids, scores 0, ends_at) |
| `pk.updated` | `score` | `accumulate` | snapshot with live scores |
| `pk.updated` | `settled` | `settle` | snapshot + `winner_id` / `draw` |

Single event name (`pk.updated`) with a `phase` discriminator (matches the Goal's "`pk.updated` WS"). Best-effort (the gateway's `io` is null in tests → no-op; a dropped broadcast never rejects into a committed mutation).

## 8. Tests added (`pk.service.test.ts`, 12 — service-level, real DB + BullMQ)

*Start:* creates an active snapshot with correct sides/zero scores/`endsAt` **and** enqueues the delayed settle job (asserted by `jobId`); refuses a second active battle (`pk_active`); rejects equal sides / non-positive duration / missing room.
*Accumulate (gift-send hook):* a gift to a competitor scores the right side; a non-competitor / non-positive amount is inert; no active battle is inert; **25 concurrent accumulates sum exactly** (2500); a gift after settle adds no late score.
*Settle:* higher score wins + battle closes (status/winnerId/settledAt); equal scores → draw (null winner); **8 concurrent settles → exactly one** (version guard); re-settle / missing battle no-op.
*Worker:* the processor settles the battle named in the delayed job (winner `b`); a foreign job name is ignored; `runPkSettle` on a settled battle is a no-op.

*Isolation:* each test creates a fresh `Room` + users, so its battle is uniquely keyed by `roomId` (the active-battle lookup sees only this test's snapshot). Delayed jobs use a unique per-battle `jobId` (BIGSERIAL pk id, never reused) and the start-test removes its job. **Verified stable across two consecutive isolated runs (12/12 each).**
