## 4. GiftPool design

- **A pool is config-as-data.** `id` matches the `Gift.poolId` scalar (a lucky gift declares which pool its spend feeds). `threshold` is the payout trigger; **values are blocked on capture #3**, so the table ships **empty/dark** and `enabled` defaults **false**.
- **Feature flag = `GiftPool.enabled`.** Off (default) ⇒ every operation is a no-op (see §5/§6). This is the "ship flagged/dark, feature-flag off = inert" requirement, self-contained (no `Setting` dependency).
- **Winner selection** (minimal, deterministic, pending capture #3): the **last contributor** — `lastContributorId`, stamped by `accumulate`. A scalar ref (no FK), consistent with the schema's other user refs.
- **Audit** = the append-only `WalletLedger` row (the codebase's canonical money-audit trail, same as gift/lucky/vip/decoration) **plus** the pool-state stamps `lastPayoutAt` / `lastPayoutAmount` / `payoutCount`. No separate `GiftPoolPayout` table (your confirmation).

## 5. Jackpot flow — accumulate

`accumulate(poolId, coins, { userId?, roomId? })`:

1. Ignore a non-positive `coins`.
2. **Atomic increment** — one `updateMany({ where:{ id, enabled:true }, data:{ amount:{increment:coins}, version:{increment:1}, lastContributorId:userId } })`. Postgres serializes concurrent row updates, so **N concurrent accumulates sum EXACTLY** (no lost updates) — this is the "concurrent accumulates don't race" guarantee, via the DB atomic-increment path (the "counter" of the "optimistic version / counter + snapshot" note; `version` is the optimistic token settle keys off).
3. **Inert when disabled/missing:** a disabled or non-existent pool matches **0 rows** ⇒ `applied:false`, **never throws**.
4. Best-effort `pool.updated` WS to `room:<roomId>` when a room context is supplied (io=null in tests ⇒ safe no-op).

**Note — wiring is deferred (in scope, on purpose):** the T2.4 file list is `gift-pool.service.ts` + `pool-settle.ts` + schema + tests; it does **not** include `gift.routes.ts`/`gift.service.ts`. So `accumulate` is defined + tested here, but its **call from the live lucky-send path is deferred** (that edit touches gift.routes/service — outside the file list, and you confirmed "no change to sendGift/gift.routes"). Because the feature ships **dark**, it is inert regardless until capture #3 lands the pool config **and** a follow-up wires the call. This mirrors T2.2 (the vip sweep's boot wiring was likewise deferred).

## 6. Settlement logic — settle

`settle(poolId)`:

1. Snapshot the pool. **Guard:** if missing → `missing`; if `!enabled` → `disabled` (**feature-flag off = no payout**); if `amount <= 0` or `amount < threshold` → `below_threshold`. All return `settled:false` without touching money.
2. Inside `serializableTx`, a **version-guarded reset**: `updateMany({ where:{ id, version: snap.version, enabled:true, amount:{ gte: threshold, gt: 0 } }, data:{ amount:0, version:{increment:1}, lastPayoutAt, lastPayoutAmount:payout, payoutCount:{increment:1} } })`.
   - If `count === 1` → **we won the crossing**. A concurrent settle, or an accumulate that bumped `version` in between, matches **0 rows** and no-ops. ⇒ **a single threshold crossing yields exactly one payout** (the "single payout" guarantee).
3. On the win, **credit the winner** (`lastContributorId`): upsert wallet, `coins += payout`, and write **one `WalletLedger` row** (`currency:0 coins`, `delta:payout`, `reason:POOL_PAYOUT=10`, `refType:'gift_pool'`, `refId:poolId`) — the money entry **and** the audit trail. A pool with **no contributor** still resets (amount retired) but pays nobody / writes no ledger row.
4. Best-effort `pool.payout` WS to the winner via `emitToUser`.

**Concurrency proof (tested):** 8 parallel `settle` on one over-threshold pool ⇒ exactly **1** `settled:true`, exactly **1** ledger row, winner credited **once**, `payoutCount === 1`.

## 7. Worker — `pool-settle.ts`

BullMQ repeatable `gifts:pool-settle` (QUEUE.gifts, T1.3 infra), default every 60s:
- `runPoolSettleSweep()` — scans `enabled` pools and calls `settle()` on each (below-threshold/empty pools no-op inside settle); returns `{ scanned, settled, paid }`.
- `poolSettleProcessor` — runs the sweep when it sees the `gifts:pool-settle` job (ignores other gifts-queue jobs).
- `registerPoolSettleWorker()` + `schedulePoolSettle()` — the T1.3 `registerWorker` / `scheduleRepeatable` hooks. **Defined + tested, NOT wired into `workers/index.ts` main** (the same deferral as T2.2 — boot registration is out of scope here; the feature is dark anyway).

## 10. Tests (`gift-pool.service.test.ts`, 12 — one file by design)

*Accumulate:* concurrent 25× increment sums exactly (amount 2500, version 25, contributor recorded); disabled pool inert (`applied:false`, no change); missing pool no-throw; non-positive amount ignored.
*Settle:* threshold crossing → single payout with **ledger + audit** (one row, `reason:10`, coins credited, pool reset + `payoutCount:1` + `lastPayout*` stamped); **8 concurrent settles → exactly one payout** (version guard); re-settle a drained pool is a no-op (no double-credit); below-threshold no-op; **disabled over-threshold inert** (feature-flag off = no payout); no-contributor retires the amount but writes no ledger.
*Worker:* sweep settles the eligible pool, leaves below-threshold + disabled pools untouched, credits the winner exactly; `schedulePoolSettle` creates a removable repeatable on the gifts queue.

**One test file on purpose:** `GiftPool` is a brand-new table no other suite touches, so keeping all pool work in a single file makes the tests fully sequential and **race-free on the shared DB** (a second file running the *global* sweep in parallel could otherwise settle a pool mid-window). *Isolation:* `GiftPool.id` is a fixed `@id` (persists across runs) → pools use a random per-run `POOL_BASE` (the T2.1/T2.2 fixed-id pattern). **Verified stable across two consecutive isolated runs (12/12 each).**
