## 4. Design

- **All additive, zero-break.** Every new column is nullable or `@default`ed, so the migration applies to existing rows with no backfill and no downtime.
- **No FK / no relations (approved deviation).** All 6 reference-style ids (`exclusiveUid`, `tabId`, `poolId`, `themeId`, `miniGameId`, `invitedById`) are plain nullable scalars — **not** `@relation` FKs. Rationale: (a) true zero-break (no constraint validation against existing rows); (b) avoids editing other models (`User`, etc.) with back-relations, which would widen scope; (c) nothing consumes them yet. The task note ("FKs `NOT VALID`") is deferred to the first real consumer task; documented as a conscious choice.
- **Level/exp columns non-null defaulted** (`roomLevel`, `roomExp`, `nobleLevel`) to match the existing convention (`charmLevel`/`wealthLevel`/`vipLevel`); everything else nullable.
- **Storage only.** No read or write path added. Verified: **no service, route, or test references any of the 27 columns** (a grep only matched the pre-existing separate `Announcement` model, not `Room.announcement`).
