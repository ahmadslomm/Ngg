## 3. What was built

A single-purpose concurrency-safe idempotency wrapper in `src/lib/idempotency.ts`, modeled on the atomic `SET … NX PX` nonce guard already used in `lib/sign.ts` — so it fits the codebase's existing Redis idiom rather than introducing a new one.

**API:**
- `withIdempotency<T>({ key, scope?, ttlMs? }, fn): Promise<T>` — runs `fn` **at most once** per `(scope,key)`; returns the identical result on the first call and every replay.
- `idemKeyOf({ key, scope? }): string` — the full Redis key (`idem:{scope}:{key}`), exported for inspection/invalidation.

**Mechanism (4 states):**
1. **Claim** — `SET idem:{scope}:{key} <pending> NX PX ttl` atomically claims the slot for the first request.
2. **Publish** — after `fn` resolves, overwrite the slot with the serialized result using `KEEPTTL` (result cached, replay window preserved).
3. **Replay** — a later request finds the completed slot and returns the cached result **without running `fn`** (the core double-charge guard).
4. **Concurrent duplicate** — a request that finds the slot still `<pending>` is rejected `AppError('idempotency_in_progress', 409)` so the client retries after the original settles.
5. **Failure release** — if `fn` throws, the claim is `DEL`eted so a legitimate later retry can re-attempt (a failed money op is never left stuck as pending, nor is a failure cached).

### Design decisions (why it fits, not just works)
1. **Reuses the shared Redis idiom.** Same atomic `SET … NX PX` primitive as `lib/sign.ts`'s nonce replay guard — no new pattern, no new client (uses the existing `lib/redis.ts` singleton).
2. **Reuses `AppError`.** The in-progress case throws `AppError('idempotency_in_progress', 409)`, rendered by the existing global error handler into the standard `{ code, message }` envelope (409 → 4090).
3. **BigInt-safe caching.** Money payloads carry bigint balances; the result is stored with a bigint→string replacer (mirroring `errors.ts serialize`). **Both** the first-call and replay paths return the JSON-normalized value, so "same key → same result" holds byte-for-byte — the true idempotency invariant. Documented that callers pass the client-facing (already-shaped) response as `fn`'s result, exactly as routes do before `reply.send`.
4. **Scope isolation.** The redis key is namespaced by `scope` (e.g. `wallet:recharge:{userId}`) so a UUID replayed on a different endpoint or by a different user cannot satisfy an unrelated operation — a small, honest hardening for money endpoints.
5. **Fail-safe, not fail-open.** A crash between claim and publish leaves a `<pending>` slot that expires with the TTL (bounded), then re-runs — it never returns a wrong/duplicate charge and never locks forever.

**Scope discipline:** the helper is **not wired into any endpoint yet** — adoption belongs to T1.15 (gift send), T2.1 (VIP purchase), T3.3 (recharge). T1.2 delivers the primitive + tests only.

The 7 new cases cover the task's acceptance criteria and the safety edges:
- **same key twice → first result, `fn` runs once** (call counter asserted == 1).
- **different keys independent** (both `fn`s run; counter == 2).
- **scope isolation** — same key under `wallet` vs `gift` scopes returns distinct results.
- **bigint round-trip** — `900n` replays as `'900'` consistently on both paths.
- **concurrent duplicate → 409 `idempotency_in_progress`** (real gate: first call blocks inside `fn`, second is rejected, then first completes).
- **TTL applied + no permanent lock** — `pttl` in `(0, ttlMs]`; after slot deletion the same key re-runs (deterministic, no flaky wall-clock wait).
- **failed `fn` releases the claim** — first call throws, retry actually runs and succeeds (no cached failure, no stuck pending).
