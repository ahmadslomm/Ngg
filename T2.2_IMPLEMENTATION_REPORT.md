## 4. Expire-sweep flow

```
vip:expire-sweep (repeatable, hourly)
  → vipExpireProcessor → runVipExpireSweep(now)
      members = Profile where vipLevel > 0           (active members are a cheap no-op)
      for each member: sweepUser(userId, now)

sweepUser(userId, now):
  activeHistories = VipHistory where expiresAt > now  (level desc)
  activeTop       = activeHistories[0]                (the surviving tier, if any)
  activeItemIds     = ∪ benefits.decorations of DISTINCT active levels     (still covered)
  vipConfiguredIds  = ∪ benefits.decorations of ALL the user's levels       (ever granted)
  revokeCandidates  = vipConfiguredIds − activeItemIds
  for itemId in revokeCandidates:
     row = UserDecoration[userId,itemId]
     if row && row.expiresAt != null && row.expiresAt <= now:   # actually lapsed
        (tx) if row.equipped: clear Profile[KIND_PROFILE_COL[kind]] where it == row.item.url
             delete UserDecoration row
  # repair cache to the true active state
  Profile.vipLevel  = activeTop?.level  ?? 0
  Profile.vipExpireAt = activeTop?.expiresAt ?? null
```

## 5. Revoke logic — identifying vip-sourced decorations (no schema marker)

A `UserDecoration` is revoked only when **all three** hold:
1. **(configured)** its item id is in the union of `benefits.decorations` across the user's VIP tiers;
2. **(uncovered)** it is **not** in the union for any still-active tier (so an active/higher tier that also grants it keeps it);
3. **(lapsed)** the row itself has expired (`expiresAt != null && ≤ now`).

This precisely targets rows a VIP granted (finite `expiresAt` = membership expiry) that are no longer covered, while sparing:
- **purchased permanent** decorations (`expiresAt = null`) — even if a tier also lists them;
- **purchased/longer-window** decorations still in the future (grant never shortened them);
- decorations **still covered** by an active tier.

Revoke = **delete** the row (perk removed) + clear the equipped `Profile.*Url` cache column **only if it still points at that item's art** (never clobbers a different equipped decoration of the same slot). Cache repair sets `vipLevel`/`vipExpireAt` to the surviving active tier (or 0/null).

**Idempotency:** a re-run finds the row already deleted (skipped) and the cache already correct (re-set to the same value); once downgraded to 0 the member drops out of the `vipLevel > 0` scan entirely. Proven by test (second `sweepUser` → `downgraded:false, revoked:0`).

## 6. Queue / worker

- **`scheduleRepeatable(queue, action, everyMs, data?)`** (new, `queue/index.ts`): `getQueue(q).upsertJobScheduler("<q>:<action>", { every: everyMs }, …)`. Keyed by the scheduler id → calling it every boot is idempotent. **`removeRepeatable(queue, action)`** removes it (ops/tests).

Both are called at worker bootstrap (a one-line boot wiring belongs to the worker-process finalize step; **`workers/index.ts` was not modified** as it is outside the T2.2 file list — the plumbing to register/schedule is complete and unit-tested here).

## 8. VIP + grant revoke summary

| State at sweep | Tier (`Profile.vipLevel`) | Granted decoration | Equipped cache |
|---|---|---|---|
| Top tier lapsed, none active | → **0** (`vipExpireAt` → null) | **revoked** (deleted) | cleared |
| Lapsed to a lower still-active tier | → lower level (its expiry) | items only the lapsed tier granted **revoked**; lower-tier items kept | cleared for revoked only |
| Still active | unchanged | kept | unchanged |
| Purchased permanent (also tier-listed) | tier may downgrade | **spared** (null expiry) | unchanged |

## 9. Tests added (`vip-expire.test.ts`, 6)

1. **expired grant → downgrade to 0 + decoration revoked + cache repaired; idempotent re-run** (the task's required scenario).
2. **equipped** vip decoration → revoke clears the matching `Profile.avatarFrameUrl`.
3. **still-active** member → no revoke, no downgrade.
4. **permanent (bought)** decoration a tier also lists → tier downgrades but the decoration is **spared**.
5. **global `runVipExpireSweep`** downgrades our lapsed member and returns counts.
6. **`scheduleVipExpireSweep`** creates a repeatable scheduler on the `vip` queue (then removable).

*Realistic lapse:* the tests age **both** `VipHistory.expiresAt` and the granted `UserDecoration.expiresAt` into the past (as a natural expiry does), not just the history. Levels use a random per-run `VipLevel.level` base (the fixed-`@id` isolation fix from T2.1).
