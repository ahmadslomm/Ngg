## 4. What was hardened (and why each was necessary)

### (a) Single-use refresh rotation — the substance of "rotate"
**Before:** `/auth/refresh` verified the refresh token and issued a *new* pair, but **never invalidated the presented token** — so a captured/replayed refresh token stayed valid until its own 30-day expiry. That is rotation in name only.
**After:** the presented refresh token's `jti` is denylisted (until its own `exp`, self-cleaning) *as* the new pair is minted, so a refresh token is **single-use**. Directly fulfills the task goal "issue/**rotate**".
- Extracted `revokeRefresh(payload)` — shared by `/auth/refresh` (rotation) and `/auth/logout`, removing duplicated `exp → TTL` math.
- Behavior change (intentional, in-scope): reusing an already-refreshed token now returns `401 invalid_refresh_token`. API **shape** unchanged. The existing "logout revokes…" test still passes (verified).

### (b) Race-safe provider→identity upsert — the substance of "upsert"
**Before:** login did `findUnique(...).catch(() => null)` then `create`. Two problems: the `.catch(() => null)` **masked DB errors** and would proceed to spuriously create a user; and find-then-create is **not atomic** — two concurrent first-logins for the same credential both miss the lookup and one hits a unique-constraint violation → 500.
**After:** `resolveIdentityUser(type, providerUid, nick)`:
- looks up the identity (no error-swallowing) → returns its `userId` if present (the common idempotent path);
- otherwise creates `user + identity + profile + wallet`, and if that create hits a Prisma **P2002** unique violation ("another request just created it"), **re-reads** the identity and returns its `userId` instead of 500-ing.
- `isUniqueViolation(e)` duck-types `code === 'P2002'` to avoid a new Prisma-error import.
- Fulfills the task goal "provider→identity **upsert**". Happy path and repeat-login response are unchanged; only the concurrent-race outcome improves (success instead of 500). Also trimmed a wasteful `include: { user: { include: { profile: true } } }` down to `select: { userId: true }` (only the id was ever used).

## 5. What I deliberately did NOT change (scope discipline)

| Item | Why left alone |
|---|---|
| **Inline error returns** (`reply.code(401).send({ code: 4010, … })`) not converted to `throw new AppError(...)` | The test harness (`buildTestApp`) registers **no** `setErrorHandler`, so a thrown `AppError` would surface as a 500 and break the auth tests. The inline envelope `{ code: 4010, message }` is already **identical** to what the production `AppError` handler emits for status 401. Converting would add risk for zero shape change. |
| **`JWT_REFRESH_SECRET` declared but unused** (refresh is signed with the access secret) | Using a distinct refresh secret requires `@fastify/jwt` namespacing — an infrastructure change to `server.ts` registration, outside minimal T1.5. Documented as a recommendation (§7). |
| **`server.ts` authenticate decorator** | Already correct: `req.jwtVerify()` rejects expired tokens, and `payload.t === 'r'` rejects a refresh token used as access. No change needed; T1.5 only confirms it via a test. |
| **New service file / DB / migration / queue / event-bus** | Out of scope by the task rules. |

The 4 new cases (in `auth.api.test.ts`, new `describe('auth token lifecycle (T1.5)')`):
- **login issues a pair** — `access_token` + `refresh_token` present, non-empty, distinct, plus `uid`.
- **refresh rotates + single-use** — a new refresh token distinct from the old; the **old** token is rejected on reuse (`401 invalid_refresh_token`); the new token still refreshes.
- **provider→identity upsert idempotent** — same `(provider, credential)` twice returns the **same `uid`** (no duplicate user).
- **expired access rejected** — a self-contained probe with the real `@fastify/jwt` `req.jwtVerify()` gate (mirroring the `server.ts` decorator): a token with a past `exp` → 401; a fresh token → 200.

The pre-existing security tests (logout revokes; login brute-force rate-limited 429) still pass unchanged.
