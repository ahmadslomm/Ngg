## 3. Implementation

Added a small, diff-reviewable wiring helper and called it from the worker `main()`:

```ts
import { registerWalletReconcileWorker, scheduleWalletReconcile } from './jobs/wallet-reconcile.js';

// The ONLY worker wired at boot is the read-only wallet-reconcile shadow job.
export async function wireDailyShadowJobs(): Promise<void> {
  registerWalletReconcileWorker();   // register the consumer (started by bootstrap)
  await scheduleWalletReconcile();   // upsert the nightly repeatable (idempotent)
}

async function main(): Promise<void> {
  log('info', 'worker_boot', { concurrency: DEFAULT_CONCURRENCY });
  await wireDailyShadowJobs();        // ← register + schedule BEFORE bootstrap
  bootstrap();                        // ← starts a Worker on QUEUE.reconcile (unchanged)
  for (const sig of ['SIGTERM', 'SIGINT'] as const) { … }              // unchanged
}
```

- `registerWalletReconcileWorker()` pushes the reconcile processor into the existing worker registry; the **untouched** `bootstrap()` then starts a BullMQ `Worker` on `QUEUE.reconcile`.
- `scheduleWalletReconcile()` = `upsertJobScheduler` (idempotent) → a nightly (24h) `reconcile:wallet` job. Safe on every boot.
- The `wireDailyShadowJobs()` body is the single source of truth that **only** reconcile is wired — it calls no other worker's register/schedule.
- The import creates an `index ↔ wallet-reconcile` cycle, which is safe: both sides use the other's bindings only inside function bodies (runtime), never at module-evaluation time. `tsc` build passes.

## 4. Tests (`workers/index.test.ts`, 1)

Asserts `wireDailyShadowJobs()` creates the `reconcile:wallet` scheduler on `QUEUE.reconcile`, that a second call does **not** duplicate it (idempotent upsert), and cleans up. **Light:** it does not call `bootstrap()` / spawn the worker process / start BullMQ Workers — only the schedule side effect.

*Design note:* the "only reconcile wired" guarantee is asserted via the `wireDailyShadowJobs()` **body** (diff-reviewable), not via a cross-queue Redis snapshot — a snapshot would be flaky because other suites (vip-expire, gift-pool) transiently create+remove their own schedulers on the vip/gifts queues during a parallel run.
