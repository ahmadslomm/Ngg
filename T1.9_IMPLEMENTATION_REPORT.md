## 4. What was built

### Password (contract §3.2 "password match if isLocked")
- **Storage:** create hashes the plaintext password with a **keyed HMAC-SHA256** (`hashRoomPassword`, server secret) into the existing `Room.passwordHash`, and sets `isLocked`. A DB leak alone can't reverse a room join-code; room passwords are low-value codes, not user credentials.
- **Enforcement:** `RoomService.join(roomId, userId, password?)` — a locked room requires a matching password (`verifyRoomPassword`, timing-safe compare) or returns `wrong_password` (→ 403). Unlocked rooms join with no password.
- Both repos (Prisma + in-memory) share the same hash helper, so the exact same behavior is tested in memory and runs on Prisma.

### Tokens (contract §3.1/§3.2)
- **`rtc_token`** minted via the existing `issueRtcToken` (agora) on create (owner → broadcaster) and join (role = seat-derived `rtcRole`). The app-cert never leaves the server.
- **`ws_ticket`** minted via the **T1.8 `issueWsTicket`** — short-lived, room-scoped, **one-time** — so the client can open the room WS channel (§3.4). Used exactly as instructed: `ws-ticket.ts` for issuance only; **not modified**.

### Ban (contract §3.2)
- Already enforced in the route via the injected `isBanned` check (moderation is external, injected) — confirmed and covered by a new test.

## 5. Design decisions

1. **Token issuers as default-valued route params** — `roomRoutes(service, isBanned, ownerProfile, mintRtc = issueRtcToken, mintTicket = issueWsTicket)`. The real libs are the defaults, so **`server.ts` needs no change** (out of scope), while tests can still override. This preserved the module's infra-agnostic route design.
2. **Password hashing in the repo layer, verify in the service** — create stores the hash (both repos, shared helper); join verifies (service, using `room.isLocked/passwordHash` from `getRoom`). Keeps the service thin and both repo paths consistent.
3. **`passwordHash` never serialized** — it lives on `RoomRecord` for the service's verify only; responses are built from `roomMeta` (explicit field pick) which excludes it. No leak.
4. **`agora_channel` moved into `roomMeta`** (not an explicit join-literal prop) — the declared `join` result type is narrow and only tolerates spread props; putting `agora_channel` in `roomMeta` compiles cleanly and additively surfaces it on join + getSeats. Channel is `room:{id}` (non-secret).
5. **String-uid reality respected** — the room module uses string uids; `issueWsTicket` only calls `.toString()` on issue (safe for string or bigint), so the route passes `req.user.id` directly. The one-time consume path (which does `BigInt`) is exercised in the test with a numeric uid.

## 8. Why `room.repo.ts` was necessary (as requested)

The service depends on the **`RoomRepo` interface + `RoomRecord`/`CreateRoomInput` types defined in `room.repo.ts`**, never on Prisma directly, so the identical logic is exercised through the **`InMemoryRoomRepo` (also in `room.repo.ts`)** in tests and Prisma in prod. Password enforcement needs `isLocked`/`passwordHash` on `RoomRecord` (for the service to check) and `password` on `CreateRoomInput` (for create), plus the in-memory repo to store them so the API test can exercise the gate. All three live in `room.repo.ts`. Any workaround (e.g. a Prisma-direct read in the route) would break the in-memory test — whose rooms don't exist in Postgres — and the infra-agnostic route contract. Hence `room.repo.ts` was the one unavoidable extra file. It carries **no schema/migration** impact — only repo types + a hash helper.
