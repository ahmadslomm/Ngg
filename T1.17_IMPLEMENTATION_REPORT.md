## 5. Assertions (the 3 required)

With `unitPrice=100, qty=2, recipients=1 → total=200`:

1. **Balance delta** — host `coins` debited by exactly `200`; guest `beans` credited by `200` (`unitPrice×qty`).
2. **Ledger pair (+ tx)** — host `WalletLedger{ reason:gift_send(1), currency:coins(0), delta:-200, refType:'gift' }` **and** guest `WalletLedger{ reason:gift_recv(2), currency:beans(1), delta:+200, refType:'gift' }`; plus `GiftTransaction{ totalCoins:200, senderId:host }` at the returned `transaction_id`.
3. **WS event** — a `gift.received` on `room:{roomId}` with monotonic `seq>0` and the existing contract data (`giftId, qty:2, senderId:host, recipientIds∋guest, totalCoins:'200'`).

## 7. Design notes

- **Real server, not the harness.** The harness (`buildTestApp`) uses an `x-test-uid` shim and skips JWT/login; a *smoke test* must prove the real login→JWT→auth chain, so this drives `build()` directly. That's the faithful reading of "login → …".
- **ws_ticket path.** The guest opens the WS with the `ws_ticket` returned by `/join` (T1.8 single-use, room-scoped) rather than a raw token — mirroring the real client handoff and auto-joining the room without a separate `room.join`.
- **Seeding coins directly.** There is no recharge endpoint in the core loop, so the host is funded via a direct wallet update + opening ledger row (the same pattern `harness.makeUser` uses), keeping ledger reconciliation intact.
- **No refactor.** `build()` is imported as-is; no source file was modified to make it testable.
