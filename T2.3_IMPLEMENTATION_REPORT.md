## 4. API / read flow

`GET /gifts` (public, optional-auth for `bag_qty` as in T1.14):

| Request | Response `data` | Notes |
|---|---|---|
| `GET /gifts` (default) | `{ items: [...] }` | **UNCHANGED** — same item shape (`id,name,category,price_coins,icon_url,anim_url,anim_type,combo_enabled,bag_qty`). No `tab_id` added. |
| `GET /gifts?group=tab` | `{ tabs: [{ id, name, sort, icon_url, items:[...] }], untabbed: [...] }` | **NEW** grouping |

**Grouping (`listGiftCatalogueGrouped`):** fetches the same gift set + bag-merge as the flat view, then buckets by the scalar `Gift.tabId` into the enabled `GiftCategory` tabs. Because there is **no FK**, referential integrity is enforced at read time:
- gift with `tabId = null` → **`untabbed`**;
- gift whose `tabId` has **no enabled tab** (missing or disabled) → **`untabbed`** (never dropped);
- a tab with no gifts → still returned with **`items: []`** (empty-tabs tolerated);
- empty `GiftCategory` table (ships empty pre-capture) → `tabs: []`, all gifts in `untabbed`.

Item serialization is the **same `serializeCatalogGift`** in both views — the grouped items are byte-identical to the flat items (no per-item tab field), so nothing about the existing catalog contract changes.
