## 3. Redis presence architecture (already built — preserved, not rebuilt)

Per your instruction "if a part already exists, don't rebuild it — just fill the gap," I did **not** re-implement presence. The existing, authoritative design:

- **Authoritative member set + count:** `RoomMember` rows in Postgres are the source of truth. `Room.onlineCount` is a denormalized cache kept **exact** by `PrismaRoomRepo.syncOnlineCount()` = `count(RoomMember)` on every `addMember`/`removeMember`. Discovery ranks/displays this. Covered by the existing `online-count.test.ts` (join/leave/idempotent re-join/non-member removal = the M1 dead-socket cleanup analog).
- **Live socket presence (Redis):** the T1.8 gateway maintains a per-room presence heartbeat so a dead socket doesn't ghost membership.
- **Dead-socket cleanup:** on an unclean disconnect the gateway's `disconnecting` handler prunes presence and calls `removeMember` → `syncOnlineCount`, so `onlineCount` self-heals.

I deliberately did **not** introduce parallel `room:{id}:online` / `:members` Redis keys (mentioned aspirationally in the task goal): they would duplicate the authoritative Postgres state and invite drift. The DB-authoritative + Redis-heartbeat split already delivers "authoritative live presence."

## 4. The permissions bitmap

**Bits (`RoomPermission`, contract §3.5):** `KICK=1, LOCK_SEAT=2, MUTE=4, EDIT_ROOM=8, MANAGE_ROLES=16`. Stored in `RoomMember.permissions` (Int, default 0).

**Semantics in `requireRoomAdmin(membership, bit)`:**
- **Owner** → always allowed (bypass).
- **Admin** → allowed, unless a required `bit` is given **and** the bitmap is **non-zero and lacks the bit** → `insufficient_permission` (403).
- **Admin with a 0/undefined bitmap** → **role fallback**: allowed (0 means "unset"). Because the column defaults to 0, every pre-existing member keeps full role powers — the bitmap can only *tighten* a member you explicitly restrict, never silently strip existing admins.
- **Listener (or non-member)** → `insufficient_role` (403).

**Plumbing:** `RoomService.requirePermission(roomId, actorId, bit)` loads the actor's `RoomMember` via `repo.getMembership` and calls `requireRoomAdmin`, converting its throw into a `ServiceResult` error code (so it composes with the existing result-based room flow rather than throwing into fire-and-forget routes). It gates the two unambiguous seat-admin actions: **`setSeatLock` (LOCK_SEAT)** and **`kick` (KICK)**.

**Deliberately not gated:** `setMute` is dual-purpose (self vs host, decided inside the FSM by actor) — gating it with a room-admin bit would break the self-mute path (`/self-mute` is the self operation; `/mute` still enforces host authority via the FSM's `isStaff`). `setRole` is owner-only (the bitmap gates Admins, not role changes). `inviteToSeat` has no dedicated bit. These keep their existing role-based FSM checks — no behavior change.

The 6 new cases (cover your four required + two safety):
- **bit ALLOWS** — Admin w/ `LOCK_SEAT` → lock ok.
- **bit DENIES** — Admin w/ `KICK` (no LOCK_SEAT) → lock → `insufficient_permission`.
- **OWNER bypass** — owner locks regardless of bits.
- **Admin without the bit** — Admin w/ `LOCK_SEAT` (no KICK) → kick → `insufficient_permission`.
- **fallback** — Admin w/ `permissions=0` → lock ok (legacy role behavior preserved).
- **Listener** — denied on role (`insufficient_role`), independent of bitmap.
