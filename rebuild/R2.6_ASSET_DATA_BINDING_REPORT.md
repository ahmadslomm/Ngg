## 0. Two findings that change the question

### 0.1 The placeholders are test residue, not seeded data — I must correct my own R2 report

R2's analysis said "every catalog row is a placeholder (`i.png`, `frame.png`, `night.png`)". That was
measured off the dev database, and it was **wrong about the cause**. The truth:

| Source | Art values |
|---|---|
| `prisma/seed.ts` (the real catalog baseline) | **explicitly `null`** — `iconUrl: null, animUrl: null, skinUrl: null, bubbleUrl: null` |
| Dev DB `Gift` | 2,048 rows `NULL` · 25 rows `i.png` · 10 rows `https://cdn.voxa.test/...` |
| Dev DB `DecorationItem` | `frame.png`, `f.png`, `x.png`, `deco-2.png`, `bub.png` … |

`i.png` / `frame.png` / `deco-N.png` / `cdn.voxa.test` are **strings written by the test suite**. There
is no `night.png` in `RoomTheme.skinUrl` either — the seed writes `null`; the value I reported came
from a test row. So: **there is nothing to "replace". The fields are empty, by design, awaiting a
catalog decision.** That does not change the conclusion, but it changes the work: this is a
*fill*, not a *repair*.

### 0.2 The catalog rows themselves are invented — this is the blocker

Auto-filling art requires rows that correspond to real original entities. They do not:

| Table | Seeded rows | Original? |
|---|---|---|
| `Gift` | Rose, Heart, Crown, Fortune Bag, Rocket, Bomb (6) | ❌ invented names/prices/ids |
| `VipLevel` | Bronze, Silver, Gold (3) | ❌ invented — the original shipped **15** VIP tiers (`waitio_vip1..15.pag`) |
| `RoomTheme` | Default, Night, Party (3) | ❌ invented; seed comment says *"PLACEHOLDER skin catalog pending capture #6"* |
| `LevelConfig` | 5 tiers × 2 ladders | ❌ *"PLACEHOLDER thresholds pending capture #4"* |

| `GiftCategory` | Hot, Lucky, Noble (3) | ❌ *"PLACEHOLDER grouping pending capture #2"* |

**You cannot bind original art to rows that are not the original items.** Mapping
`waitio_vip7.pag` onto a row named "Gold" (level 3 of 3) would be inventing a tier identity — exactly
what the rules forbid.

## 4. Answer to the question you asked

> **هل يمكن ملء الكتالوج تلقائيًا من أصول التطبيق القديم أم نحتاج قرار منتج؟**

**Neither, in the form the question assumes — and the reason is worth being precise about.**

Auto-fill is impossible, but *not* mainly because art is missing. It is impossible because **three
independent links in the chain are broken**, and a product decision only fixes the third:

1. **The rows are not the original items.** Six invented gifts, three invented VIP tiers, three
   invented themes, seven invented medal codes. No mapping onto them can be *recovered* — only
   *decided*. (Blocks: gifts, VIP, themes, medals, levels.)
2. **Some art has HIGH-confidence identity but no column to live in.** DJ tiers, friend-intimacy
   tiers, and VIP speaking rings are unambiguously named in the original filenames — and the schema
   has nowhere to put them. Fixing this is a **migration**, which R2.6 forbids. (Blocks: 4 systems.)
3. **The classes users actually see first — gift icons, medals, avatar frames — were never bundled
   at all.** They were pure CDN catalog art in the original. No amount of decision-making creates
   them; they must be either re-captured or newly authored. (Blocks: 3 systems.)

So the honest routing is:

| Need | Who resolves it | What it unblocks |
|---|---|---|
| **A live authenticated capture** of `gift.getGiftList`, `getClientGiftTabs`, `room.getRoomModelConfig`, VIP config | **You** — it hits the original operator's servers; the pipeline is built (`LIVE_API_RESPONSES/README.md`) and I have not run it and will not without your explicit go-ahead | gift ids + icons + `svga_url` + prices, the real VIP tier table, real themes — i.e. links 1 and 3 for the biggest systems |
| **A product decision** on tier art (which shield is VIP1, which emblem is which wealth grade, one ring for all couples?) | You | VIP shields, wealth emblems, CP ring, agency tags |
| **A schema change** (approval gate) for `djLevel`, friendship tier, VIP ring columns | You | the 4 HIGH-confidence orphans |
| **Authoring new art** for gift icons / medals | You or a designer | the never-bundled classes |

**Recommendation.** The capture is worth far more than the other three combined — it converts links 1
and 3 from "decide" to "recover" for gifts, VIP and themes, which is most of the catalog. Until it
exists, filling the catalog means *authoring a new product*, not *reconstructing the original*, and I
would be inventing every id I wrote. That is the line I have stopped at.

**Nothing was modified. No commit.**
