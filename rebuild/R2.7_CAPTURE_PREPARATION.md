## 3. Format finding — decorations are **zip bundles**, not images

From the already-captured `user.getUserinfo`:

```
avatarFrame : https://ufile.zaffalive.com/uc/zip/goods_1575…zip?srcType=3
chatBubble  : https://ufile.zaffalive.com/uc/zip/goods_288c…zip?srcType=1
infoBgImg   : https://ufile.zaffalive.com/uc/zip/goods_bd79…zip?srcType=2
```

Worn decorations are delivered as **`.zip` archives** with a `srcType` discriminator
(`1` bubble · `2` info background · `3` avatar frame — observed, not documented).

Two consequences:

1. **`AssetResolver` cannot play these.** R2.3 handles png/gif/svga/pag/mp4/lottie; `.zip` resolves
   to `AssetFormat.unknown` and renders nothing. Supporting them means download → unzip → detect the
   inner format. That is new client work, out of scope here, and worth knowing **before** you spend
   a capture on the decoration store.
2. `srcType` is a real, free kind discriminator — it is very likely the codebook that maps onto
   `DecorationItem.kind`. Not asserted: three observations from one user is not a codebook.

## 4. Three things a capture will NOT fix

### 4.1 Noble ≠ VIP
The original ran **two** systems: `Action/Noble.*` with `noble_level`, and `vip_info` / `vipName` /
`vipMedalImg` on the user DTO. The rebuild has one `VipLevel` table. Importing Noble's 15 tiers into
it **merges two products** — a decision, not a recovery. The importer therefore refuses unless run
with `--allow-noble-as-vip`.

*(Noted, not asserted: 15 Noble tiers and 15 bundled `waitio_vip{1..15}.pag` frames is a suggestive
match. It is not evidence.)*

### 4.2 Room themes have no catalogue endpoint
Nothing in the 280 recovered endpoints lists themes. `mall.buyTheme` / `useTheme` are **writes**;
`room.getRoomInfo` shows only the theme a given room already wears. You could scrape N rooms and
collect distinct themes, but that enumerates *what is in use*, not the catalogue — and the DTO
carries **no theme id**, so rows could not be keyed. The importer rejects `RoomTheme` rows for this
reason.

### 4.3 Two systems are account-gated, not capture-gated
`Action/SVip.getPrivilege` and `Action/SVip.getInfo` returned `status=error`, and
`Action/Anchor.getGuildInfo` returned an empty array — the test account is not an SVIP and owns no
guild. Re-running the same capture with the same account changes nothing.

## 5. The importer

**`rebuild/backend/tools/catalog-import/`** — standalone, outside `src/` (excluded from the server
build; `npm run typecheck` unaffected).

```
extract.ts        pure extractors + validator   (no DB, no network, no fs)
import.ts         CLI: read → extract → validate → report → JSON → optional --apply
extract.test.ts   24 tests, all passing
```

```bash
# dry run (default) — reads captures, writes catalog.import.json, touches nothing
npx tsx tools/catalog-import/import.ts --in ../../analysis/h5_api/responses

# write to the database (gated)
npx tsx tools/catalog-import/import.ts --in <dir> --apply
```

### Idempotency with no migration

Every target table already has a natural key the **original id** can occupy, so imports replay
safely and every row traces back to its capture — with no new column:

| Table | Key | Source |
|---|---|---|
| `Gift.id` | explicit BigInt pk | original `gid` |
| `DecorationItem.id` | explicit BigInt pk | original goods id |
| `VipLevel.level` | level **is** the pk | Noble `level` |
| `LevelConfig` | `@@unique([kind, level])` | ladder kind + level |
| `Medal.code` | unique | `zl_<original id>` — prefixed so it can never collide with a seeded code |

### How the no-invention rule is mechanical, not aspirational

- A record is emitted **only** when the capture supplies its identity — `validate()` rejects any row
  without a `sourceId` rather than synthesising one (`extract.test.ts` pins this).
- A field the capture did not carry stays `undefined`, and `clean()` strips undefined keys before
  every upsert — so an import **never overwrites existing data with a guess**, and a later, richer
  capture simply fills the gaps.
- Codebooks that are not proven are **not applied**: `DecorationItem.kind` is left unset (rows
  without it are skipped on apply), and `svga_type` is reported in `extra` rather than written to
  `Gift.animType`, because the two codebooks are not known to agree.
- Ambiguity is surfaced, not resolved: slot-ordinal magicBox prizes are refused; `icons_map` ranges
  are kept unexpanded; the Noble/VIP merge needs an explicit flag.
