## 3. What was built

A pure **authorization decision layer** in `src/lib/authz.ts` — no JWT verification, no DB, no Fastify coupling — callable from routes, services, and the WS gateway alike.

- **`requireUser(req)`** → returns the user id as `bigint`; throws `unauthorized` (401) when `req.user.id` is absent. Coerces string/number/bigint ids.
- **`requireSelf(req, targetId)`** → authenticates then asserts identity == target; throws `forbidden` (403) otherwise. For self-only resources (wallet, settings, private inventory).
- **`requireRoomAdmin(membership, permission?)`** → Owner always passes; Admin passes, and when a specific `permission` bit is required it is enforced **only if** the membership carries a `permissions` bitmap; Listener denied (`insufficient_role` 403), or `insufficient_permission` (403) when a present bitmap lacks the bit.
- **`requirePlatformAdmin(req)`** → returns admin id; throws `admin_unauthorized` (401) when `req.admin` absent.
- **Constants:** `RoomRole {Listener:0, Admin:1, Owner:2}` and `RoomPermission {KICK:1, LOCK_SEAT:2, MUTE:4, EDIT_ROOM:8, MANAGE_ROLES:16}` (contract §3.5).

### Design decisions (why it fits the codebase, not just works)
1. **Single source of truth for tokens preserved.** JWT verification + suspension checks stay in the existing `authenticate` / `authenticateAdmin` decorators (`server.ts`). These guards only assert the *already-resolved* identity — no duplicated `jwtVerify`, no drift.
2. **Reuses the shared `AppError`.** Every failure throws `AppError(code, status)`, so the existing global `setErrorHandler` renders the same `{ code, message }` envelope as every other route (401→4010, 403→4030). No new error path introduced.
3. **Correct layering.** `lib/` sits at the bottom layer and must not import from `modules/`; the role tiers are re-declared as local constants (mirroring the canonical `Role` enum in `modules/rooms/seat-state.ts`) rather than importing upward.
4. **Forward-compatible with the unbuilt `permissions` column.** `RoomMember.permissions` does not exist yet (arrives in T1.16/T1.11). Until a membership carries a `permissions` bitmap, `requireRoomAdmin` falls back to role-only — so turning the bitmap on later can **only tighten** access, never loosen it. Verified by a dedicated test.
5. **Structural request shapes.** Guards accept a minimal `{ user?: { id } }` / `{ admin?: { id } }` / `{ role, permissions? }`, so a Fastify request, a plain object, or a repo row all work without adapters — which is what makes them DB-free and unit-testable per the task's "No DB needed".

**Scope discipline:** the guards are **not yet wired into any route** — route adoption belongs to T1.5 (auth), T1.11 (room-admin bitmap plumbing) and later tasks. T1.1 delivers the guards + tests only, keeping the change atomic.
