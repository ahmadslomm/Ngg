## 3. What was built

### `src/lib/ws-ticket.ts` (new)
A compact, self-contained credential — **not** a JWT, so it can never be confused with an access/refresh token:
- **`issueWsTicket({ userId, roomId }, ttlSec=60)`** → `base64url(payload).hmac`, where `payload = { u, r, j(jti), exp }`, signed with HMAC-SHA256 over the existing **`JWT_ACCESS_SECRET`** (no new config/env).
- **`verifyWsTicket(ticket)`** → stateless signature (timing-safe compare) + expiry check → `{ userId, roomId, jti, exp } | null`. Never throws.
- **`consumeWsTicket(ticket)`** → `verifyWsTicket` + an atomic Redis single-use guard: `SET wsticket:used:<jti> 1 EX <remaining> NX`. First caller wins; a replay returns `null`. The guard key self-expires at the ticket's own `exp`, so it never leaks.

### `src/realtime/gateway.ts` (modified — additive, backward-compatible)
- **Connect middleware** now checks for a **ticket** first (handshake `auth.ticket` or `?ticket=` query, per contract §3.4). If present: `consumeWsTicket` → on failure `unauthorized`; then a **ban/suspend re-check** via the existing `hooks.authorizeJoin` → on failure `forbidden`; then bind `uid` and stash `ticketRoom`. **If no ticket, it falls through to the unchanged JWT `verifyToken` path.**
- **On connection**, a ticket socket **auto-joins its room** (`room:{roomId}`) — the WS is room-scoped by construction (§3.4), so no separate `room.join` round-trip is needed.
- **`joinRoom(socket, uid, roomId, reauthorize)`** helper extracted from the old `room.join` body and reused by both the ticket auto-join (`reauthorize=false`, ban already checked on connect) and the `room.join` event (`reauthorize=true`, unchanged H2 behavior). Presence + `room.joined` broadcast are identical to before.

### `src/realtime/realtime.test.ts` (modified)
Three new cases mapping to the spec's test ("valid ticket connects+joins; invalid/expired rejected; broadcast reaches all sockets across two adapter nodes"):
- **valid ticket** connects and **auto-joins** `room:500`, then receives an `emitRoomEvent` broadcast — with the token path disabled (`verifyToken` returns null), proving the ticket alone authenticated.
- **invalid** (`'not.a.ticket'`) and **expired** (`ttl=-10`) tickets are both rejected with `unauthorized` on connect.
- **cross-node fan-out**: two independent `initRealtime` nodes share the Redis adapter; each client auto-joins `room:600` via its own ticket; a broadcast emitted from **node A** reaches **node B's** client through the adapter.

## 4. Design decisions

1. **Additive ticket path, not a replacement (the key decision).** Replacing the JWT connect path with ticket-only would (a) require editing `server.ts` (out of scope), and (b) break **all** production WS connections until T1.9 mints tickets. So the ticket path is layered **above** the existing JWT path: ticket if present, else JWT. This implements the contract's §3.4 auth without changing architecture or touching `server.ts`, and keeps all five pre-existing realtime tests green.
2. **`initRealtime` signature unchanged.** No caller (`server.ts`) needs editing. The gateway imports `consumeWsTicket` directly rather than taking it via DI, matching how it already imports `redis`.
3. **Membership + ban split, as the contract intends.** Membership is proven by the ticket itself (minted only after `/join`'s membership/ban check in T1.9); **ban/suspension is a fast-changing condition re-checked on connect** via the existing `authorizeJoin` hook. No new module import into the gateway.
4. **Single-use via Redis, TTL-bounded.** "One-time wsTicket" (T1.9's wording) is enforced here at the consumption point, self-cleaning at the ticket's `exp`.
5. **Reused `JWT_ACCESS_SECRET`; no new env** — avoids editing `env.ts` (out of scope). The ticket format is deliberately distinct from a JWT.
6. **`chat` relay left as-is.** Chat is authoritative via REST → `emitRoomEvent` broadcast (gateway header: "Authoritative state changes always arrive via REST"). Adding a client-emitted `chat` socket event would bypass moderation and change architecture — forbidden by the constraints. Chat broadcasts already reach ticket connections (same room channel; proven by the broadcast test). `heartbeat` relay is the existing socket handler, unchanged.
